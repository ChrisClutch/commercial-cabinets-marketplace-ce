================================================================================
  THE FORGE SALEM — BACKEND IMPLEMENTATION PLAN
  forgesalem.com  |  Stack: Supabase (Postgres + Auth + Storage + RLS)
================================================================================

This document outlines everything needed to move the site off localStorage and
sessionStorage and onto Supabase. Nothing here is implemented yet.
Read top to bottom — later sections depend on earlier ones.


--------------------------------------------------------------------------------
  SECTION 1 — WHAT'S BROKEN RIGHT NOW (AND WHY)
--------------------------------------------------------------------------------

1. Admin credentials are hardcoded in plain text inside AdminLoginPage.tsx.
   Anyone who views the compiled JS bundle can read the username and password.

2. The "auth guard" is just a sessionStorage flag ('forge_admin': 'true').
   Any user can open DevTools and set that flag themselves to access the admin.

3. Community messages (text + photos) are stored in localStorage — meaning:
   - Data lives only in one browser on one device. Admin changes on one machine
     don't appear on another.
   - Photos are base64-encoded blobs inside localStorage, which has a ~5–10 MB
     cap per origin. A few photos will hit that limit and start throwing errors.
   - Submitting a message on the public site and reviewing it in the admin panel
     only works if both happen in the same browser. In production this is useless.

4. The bathroom code is also localStorage-only — same cross-device problem.

5. There is no rate limiting. Anyone can spam the community board form.

6. There is no file type or file size validation on photo uploads beyond the
   browser's "accept" attribute, which is trivially bypassed.


--------------------------------------------------------------------------------
  SECTION 2 — TECH STACK
--------------------------------------------------------------------------------

Primary: Supabase (no custom backend server needed)

  SUPABASE SERVICES USED
  ──────────────────────
  Supabase Postgres     — hosted PostgreSQL database, managed via dashboard.
  Supabase Auth         — handles admin login (email/password). Replaces the
                          hardcoded credentials and sessionStorage flag entirely.
  Supabase Storage      — file bucket for community board photos. Files are
                          stored as URLs, not base64 blobs.
  Row Level Security    — Postgres policies that enforce who can read/write what,
  (RLS)                   replacing what a custom JWT middleware would do.
  Supabase Edge Funcs   — optional Deno functions for logic that shouldn't run
                          client-side (rate limiting, email notifications, image
                          processing). Only add these if needed — RLS + client
                          SDK covers most of the app.

  FRONTEND
  ────────
  @supabase/supabase-js — the official JS client, called directly from React.
  Vite environment vars (VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY) for config.

  EMAIL (optional — new message notifications to admin)
  ─────
  Supabase Edge Function triggered by a Postgres webhook on INSERT into
  community_messages, calling Resend or Sendgrid to email the admin.

  NOTE ON A CUSTOM SERVER
  ───────────────────────
  A separate Node.js/Express backend is NOT needed for this project's scale.
  Supabase's RLS policies + the anon key handle authorization on every query.
  If rate limiting or server-side image resizing become a hard requirement,
  add a single Supabase Edge Function rather than spinning up a full server.


--------------------------------------------------------------------------------
  SECTION 3 — DATABASE SCHEMA
--------------------------------------------------------------------------------

Run these in the Supabase SQL editor (Dashboard → SQL Editor → New query).

  TABLE: community_messages
  ─────────────────────────
  CREATE TABLE community_messages (
    id            UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
    name          VARCHAR(120)  NOT NULL DEFAULT 'Anonymous',
    message       TEXT          NOT NULL,
    photo_url     TEXT          NULL,       -- public URL from Supabase Storage
    status        TEXT          NOT NULL DEFAULT 'pending'
                                CHECK (status IN ('pending','approved','denied')),
    submitted_at  TIMESTAMPTZ   NOT NULL DEFAULT NOW(),
    reviewed_at   TIMESTAMPTZ   NULL
  );
  CREATE INDEX idx_community_status ON community_messages(status);

  Notes:
  - photo_url stores the public storage URL, not a base64 string.
  - reviewed_at is set to NOW() when the admin approves or denies a message.


  TABLE: settings  (key/value store for bathroom code and other config)
  ──────────────────────────────────────────────────────────────────────
  CREATE TABLE settings (
    key         VARCHAR(80)   PRIMARY KEY,
    value       TEXT          NOT NULL DEFAULT '',
    updated_at  TIMESTAMPTZ   NOT NULL DEFAULT NOW()
  );
  INSERT INTO settings (key) VALUES ('bathroom_code');

  Notes:
  - Extend with additional keys as needed without schema changes.


  TABLE: events  (optional — move events out of the hardcoded events.ts)
  ────────────────────────────────────────────────────────────────────────
  CREATE TABLE events (
    id          UUID          PRIMARY KEY DEFAULT gen_random_uuid(),
    title       VARCHAR(200)  NOT NULL,
    date        DATE          NOT NULL,
    venue       VARCHAR(200)  NOT NULL,
    category    TEXT          NOT NULL CHECK (category IN ('dining','events','wellness')),
    description TEXT          NOT NULL,
    created_at  TIMESTAMPTZ   NOT NULL DEFAULT NOW()
  );

  Notes:
  - Only add this table when you're ready to manage events from the admin panel.
    Until then, events.ts continues to work fine.


  ADMIN USER
  ──────────
  No admin_users table needed. Supabase Auth manages this.
  Create the admin account once via:
    Dashboard → Authentication → Users → Invite user
    (or use supabase.auth.signUp() in a one-time script)
  Use a strong password. Only one account is needed.


--------------------------------------------------------------------------------
  SECTION 4 — ROW LEVEL SECURITY POLICIES
--------------------------------------------------------------------------------

RLS is what makes it safe to call Supabase directly from the frontend.
Enable RLS on every table, then define exactly what the anon key can do.

Run in the SQL editor after creating each table.


  community_messages
  ──────────────────
  ALTER TABLE community_messages ENABLE ROW LEVEL SECURITY;

  -- Public: submit a new message (status defaults to 'pending')
  CREATE POLICY "public_insert" ON community_messages
    FOR INSERT TO anon
    WITH CHECK (status = 'pending');

  -- Public: read only approved messages
  CREATE POLICY "public_select_approved" ON community_messages
    FOR SELECT TO anon
    USING (status = 'approved');

  -- Admin: full access to all messages
  CREATE POLICY "admin_all" ON community_messages
    FOR ALL TO authenticated
    USING (true)
    WITH CHECK (true);


  settings
  ────────
  ALTER TABLE settings ENABLE ROW LEVEL SECURITY;

  -- Public: read bathroom_code only
  CREATE POLICY "public_read_bathroom_code" ON settings
    FOR SELECT TO anon
    USING (key = 'bathroom_code');

  -- Admin: full access
  CREATE POLICY "admin_all" ON settings
    FOR ALL TO authenticated
    USING (true)
    WITH CHECK (true);


  events  (if using the events table)
  ────────────────────────────────────
  ALTER TABLE events ENABLE ROW LEVEL SECURITY;

  -- Public: read all events
  CREATE POLICY "public_select" ON events
    FOR SELECT TO anon
    USING (true);

  -- Admin: full access
  CREATE POLICY "admin_all" ON events
    FOR ALL TO authenticated
    USING (true)
    WITH CHECK (true);


  Storage bucket: community-photos
  ─────────────────────────────────
  -- Create bucket in Dashboard → Storage → New bucket
  -- Name: community-photos
  -- Public: true  (so photo URLs work without signed tokens)

  -- Storage RLS (set in Dashboard → Storage → community-photos → Policies):
  --   anon  can INSERT (upload)
  --   anon  can SELECT (read/download)
  --   authenticated can DELETE (admin cleanup)

  Notes:
  - Randomize filenames on upload (use crypto.randomUUID()) — never use the
    original filename from the user's device.
  - Enforce 8 MB max in the upload call options.
  - Supabase Image Transformations (paid feature) can resize + strip EXIF on
    the fly via URL params if you need that later.


--------------------------------------------------------------------------------
  SECTION 5 — SUPABASE CLIENT SETUP (FRONTEND)
--------------------------------------------------------------------------------

  Install:
    npm install @supabase/supabase-js

  Create src/lib/supabase.ts:
    import { createClient } from '@supabase/supabase-js'
    export const supabase = createClient(
      import.meta.env.VITE_SUPABASE_URL,
      import.meta.env.VITE_SUPABASE_ANON_KEY
    )

  .env (local, never commit):
    VITE_SUPABASE_URL=https://your-project.supabase.co
    VITE_SUPABASE_ANON_KEY=your-anon-key

  The anon key is safe to expose client-side — RLS policies enforce what it
  can actually do. Never use the service_role key in the frontend.


--------------------------------------------------------------------------------
  SECTION 6 — AUTH OVERHAUL
--------------------------------------------------------------------------------

Current state:
  - Username/password hardcoded in AdminLoginPage.tsx (INSECURE).
  - Auth state = sessionStorage flag 'forge_admin' (TRIVIALLY BYPASSED).

What to replace it with:

  1. Remove ADMIN_USER and ADMIN_PASS constants from AdminLoginPage.tsx.

  2. Replace the login form submission with:
       const { error } = await supabase.auth.signInWithPassword({ email, password })
       if (error) { /* show error */ }
       else { navigate('/admin/dashboard') }

  3. Replace the auth guard useEffect in AdminWelcomePage.tsx with:
       const { data: { session } } = await supabase.auth.getSession()
       if (!session) navigate('/admin', { replace: true })

  4. Replace handleLogout with:
       await supabase.auth.signOut()
       navigate('/')

  5. The Supabase session is stored in localStorage automatically by the client.
     It uses a short-lived JWT + refresh token — far safer than a plain flag.

  6. Replace the 'forge_gate' triple-click Easter egg with a normal visible
     "Admin" link (e.g., in the footer). Real security comes from Supabase Auth
     credentials, not from hiding the login URL.


--------------------------------------------------------------------------------
  SECTION 7 — FRONTEND WIRING (WHAT TO CHANGE IN EACH FILE)
--------------------------------------------------------------------------------

  forgeStore.ts
  ─────────────
  Remove localStorage logic entirely once Supabase is wired up.
  Interim approach: keep forgeStore.ts working while migrating file by file.
  Final state: delete the file.

  InformationPage.tsx + HomePage.tsx — community board (public read)
  ──────────────────────────────────
  Replace:
    getMessages().filter(m => m.status === 'approved')
  With:
    const { data } = await supabase
      .from('community_messages')
      .select('id, name, message, photo_url, submitted_at')
      .eq('status', 'approved')
      .order('submitted_at', { ascending: false })

  HomePage.tsx + InformationPage.tsx — form submission
  ──────────────────────────────────
  Replace: saveMessages([...all, newMsg])
  With a two-step call:
    1. If image attached — upload to Storage:
         const filename = `${crypto.randomUUID()}.${ext}`
         const { data: upload } = await supabase.storage
           .from('community-photos')
           .upload(filename, file, { upsert: false })
         const photo_url = supabase.storage
           .from('community-photos').getPublicUrl(filename).data.publicUrl
    2. Insert the message row:
         await supabase.from('community_messages').insert({
           name, message, photo_url: photo_url ?? null
         })

  InformationPage.tsx — bathroom code (public read)
  ──────────────────
  Replace: getBathroomCode()
  With:
    const { data } = await supabase
      .from('settings')
      .select('value')
      .eq('key', 'bathroom_code')
      .single()

  AdminWelcomePage.tsx — community messages (admin read + update)
  ────────────────────
  Replace getMessages() / saveMessages() with:
    // fetch all (admin sees everything)
    const { data } = await supabase
      .from('community_messages')
      .select('*')
      .order('submitted_at', { ascending: false })

    // update status
    await supabase
      .from('community_messages')
      .update({ status, reviewed_at: new Date().toISOString() })
      .eq('id', id)

  AdminWelcomePage.tsx — bathroom code (admin write)
  ────────────────────
  Replace persistCode() with:
    await supabase
      .from('settings')
      .update({ value: newCode, updated_at: new Date().toISOString() })
      .eq('key', 'bathroom_code')

  events.ts — if/when you move events to the DB
  ──────────
  Replace the hardcoded array with:
    const { data: events } = await supabase
      .from('events')
      .select('*')
      .gte('date', today)
      .order('date', { ascending: true })


--------------------------------------------------------------------------------
  SECTION 8 — FILE UPLOAD SECURITY CHECKLIST
--------------------------------------------------------------------------------

  [ ] Validate MIME type client-side before upload (check file.type).
      For stronger validation, read the first bytes with FileReader and check
      magic bytes — the browser's file.type can be spoofed.
  [ ] Reject files over 8 MB before attempting the upload:
        if (file.size > 8 * 1024 * 1024) { /* show error */ return }
  [ ] Always rename to a random UUID — never use the original filename:
        const filename = `${crypto.randomUUID()}.${file.name.split('.').pop()}`
  [ ] Only allow specific extensions: jpg, jpeg, png, webp.
  [ ] Use Supabase Image Transformations for resizing/EXIF stripping if needed
      (Dashboard → Storage → Transform). Strips GPS metadata automatically.
  [ ] Storage bucket policies (set in Section 4) prevent unauthorized deletes.
