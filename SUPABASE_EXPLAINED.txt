================================================================================
  THE FORGE SALEM — SUPABASE BACKEND: PLAIN ENGLISH EXPLANATION
================================================================================

This file explains what we built, why we built it, and how it all fits together.
Written so you can come back to this later and understand exactly what is going on.


--------------------------------------------------------------------------------
  THE BIG PICTURE — WHY ARE WE DOING THIS?
--------------------------------------------------------------------------------

Right now the site stores everything in localStorage. LocalStorage is a tiny
storage area that lives inside one specific browser on one specific device.
Think of it like a sticky note on your laptop screen — only you can see it,
and if you switch computers it's gone.

That means:
  - If you approve a community message on your laptop, it won't show up when
    someone visits the site on their phone. They have a different localStorage.
  - If a visitor submits a message on the public site, you'll never see it in
    your admin panel unless they used the exact same browser as you.
  - Photos are stored as massive blobs of text (base64) inside that tiny
    sticky note storage. It fills up fast and crashes silently.
  - The admin password is written in plain text inside the app's code. Anyone
    who knows how to open browser DevTools can find it in about 30 seconds.

Supabase fixes all of this. It gives us a real database that lives in the cloud,
a proper login system, and a place to store photos — all accessible from any
device, anywhere.


--------------------------------------------------------------------------------
  WHAT IS SUPABASE?
--------------------------------------------------------------------------------

Supabase is a service that gives you several things packaged together:

  1. A PostgreSQL database
     PostgreSQL (usually called "Postgres") is one of the most widely used
     databases in the world. Think of it as a very powerful, very reliable
     spreadsheet that lives on a server. Data stored here is permanent, shared
     across all devices, and can be queried instantly.

  2. An API that talks to that database
     Supabase automatically creates a web API on top of your database tables.
     This means your React app can send requests like "give me all approved
     messages" and get back the data without you having to write a backend server.

  3. Authentication (Auth)
     A complete login system. Handles passwords, sessions, and security for you.
     You don't need to write any password-hashing code — Supabase does it.

  4. Storage
     A place to upload and host files (photos, in our case). Works like a
     simple cloud drive. Files get a public URL you can use in an <img> tag.

  5. Row Level Security (RLS)
     A way to write rules directly in the database about who can see or change
     what data. More on this below.

The reason we chose Supabase over building our own backend server is speed and
simplicity. We don't need to rent a server, write API endpoint code, or manage
deployments for what this site needs. Supabase handles all of that.


--------------------------------------------------------------------------------
  THE DATABASE — TABLES WE CREATED
--------------------------------------------------------------------------------

A database is made up of tables. Each table holds one type of data.
We created two tables:


  TABLE: community_messages
  ─────────────────────────
  This replaces the localStorage community board data.

  Each row is one message someone submitted. The columns are:

    id            A unique identifier for every message. Automatically generated.
                  Uses UUID format (looks like: a3f2c1d4-...). This ensures
                  no two messages ever have the same ID, even if submitted at
                  the exact same millisecond.

    name          The name the person entered. Defaults to 'Anonymous' if blank.

    message       The actual text of their message.

    photo_url     If they attached a photo, this holds the URL to that photo
                  in Supabase Storage. If no photo was attached, it's NULL
                  (database word for "empty / not provided").

    status        One of three values: 'pending', 'approved', or 'denied'.
                  New submissions always start as 'pending'. The admin changes
                  this in the dashboard.

    submitted_at  The exact date and time the message was submitted.
                  Automatically set to right now when a row is inserted.

    reviewed_at   The date and time the admin approved or denied the message.
                  Starts as NULL, gets filled in when the admin acts on it.

  We also created an INDEX on the status column. An index is like a book's
  index at the back — it makes searching by a specific column much faster.
  Since we constantly filter messages by status ('approved', 'pending', etc.),
  this speeds those queries up significantly.


  TABLE: settings
  ───────────────
  A simple key/value store for configuration values that the admin can change.
  Right now it just holds the bathroom code, but it can hold anything.

  Each row has:
    key         The name of the setting. Example: 'bathroom_code'
    value       The current value. Example: '1234'
    updated_at  When it was last changed.

  We pre-inserted one row: ('bathroom_code', '') so the row already exists
  and we just UPDATE its value rather than INSERT a new one each time.

  Why not just hardcode the bathroom code in the site? Because the admin needs
  to be able to change it without touching any code or doing a redeployment.


--------------------------------------------------------------------------------
  ROW LEVEL SECURITY (RLS) — THE MOST IMPORTANT CONCEPT
--------------------------------------------------------------------------------

This is the core of why Supabase is safe to use directly from the frontend.

Here's the problem it solves:

  Your React app needs an API key to talk to Supabase. That key is included
  in the JavaScript code that gets sent to every visitor's browser. That means
  anyone can technically open DevTools and see it.

  Without RLS, someone could take that key, open a terminal, and run:
    "give me ALL community messages including pending and denied ones"
    "change the bathroom code to something random"
    "delete everything"
  ...and it would work. Bad.

  With RLS, the database itself enforces rules regardless of what key is used.
  Even if someone has your API key, they can only do what the rules allow.

Here's what our rules (policies) say:


  For community_messages:
  ───────────────────────
  "public_insert" — Anyone (anon) can add a new message, BUT the status field
  must be 'pending'. This means nobody can submit a message and set it to
  'approved' themselves — it always starts in the review queue.

  "public_select_approved" — Anyone (anon) can READ messages, BUT only ones
  where status = 'approved'. Pending and denied messages are invisible to
  the public no matter what.

  "admin_all" — A logged-in admin (authenticated) can do anything: read all
  messages regardless of status, update status, delete rows, everything.


  For settings:
  ─────────────
  "public_read_bathroom_code" — Anyone can read the bathroom_code setting.
  This is how visitors on /information see the code without logging in.

  "admin_all" — Only the logged-in admin can change any setting.


  The two roles — anon vs authenticated:
  ───────────────────────────────────────
  'anon'          = any request made with the public API key (every visitor).
  'authenticated' = a request made by someone who has logged in via Supabase
                    Auth. In our case, that's only you (the admin).

  Supabase automatically knows which role applies based on whether a valid
  login session exists. You don't have to check this yourself.


--------------------------------------------------------------------------------
  SUPABASE AUTH — HOW THE ADMIN LOGIN WILL WORK
--------------------------------------------------------------------------------

Right now the admin login checks a hardcoded username and password that anyone
can find in the source code. We're replacing that with Supabase Auth.

Here's how the new flow works:

  1. Admin visits /admin and enters their email + password.

  2. The app calls supabase.auth.signInWithPassword({ email, password }).

  3. Supabase checks those credentials against its Auth system (passwords are
     stored as bcrypt hashes — a one-way scramble that can't be reversed).

  4. If correct, Supabase returns a session object containing two tokens:
       - Access token: a short-lived JWT (expires in 1 hour by default).
       - Refresh token: a longer-lived token used to get a new access token
         without making the user log in again.

  5. The Supabase JS client stores these tokens in localStorage automatically
     and attaches the access token to every subsequent database request.

  6. The database sees the request is from an 'authenticated' user and applies
     the admin_all RLS policies, giving full access.

  What is a JWT?
  A JSON Web Token is a small piece of encoded text that proves who you are.
  It's like a signed wristband at a concert — the bouncer (database) can
  verify it's real without calling the box office (a central server) every time.

  The admin session survives page refreshes because the tokens are in
  localStorage. If the access token expires, the client uses the refresh token
  to silently get a new one. The admin only needs to log in once per session.


--------------------------------------------------------------------------------
  SUPABASE STORAGE — HOW PHOTO UPLOADS WILL WORK
--------------------------------------------------------------------------------

Instead of converting photos to huge base64 strings and cramming them into
localStorage, we upload them to a Supabase Storage bucket.

A bucket is basically a folder in the cloud. Ours is called 'community-photos'.

The upload flow:
  1. Visitor picks a photo in the community board form.
  2. Before uploading, we rename the file to a random UUID (e.g. a3f2c1d4.jpg).
     We never use the visitor's original filename — it could contain weird
     characters or be used in an attack.
  3. We upload the file to the 'community-photos' bucket via the Supabase client.
  4. Supabase returns a public URL for that file.
     Example: https://abc.supabase.co/storage/v1/object/public/community-photos/a3f2c1d4.jpg
  5. We store that URL in the photo_url column of the community_messages table.
  6. Anywhere we display the message, we just use that URL in an <img> tag.

Why this is better than base64 in localStorage:
  - No storage size limit problems.
  - Photos load faster (served from a CDN, not embedded in JS).
  - The database row stays small (just a URL string, not megabytes of data).
  - Photos persist even if the user clears their browser storage.


--------------------------------------------------------------------------------
  HOW THE FRONTEND (REACT APP) TALKS TO SUPABASE
--------------------------------------------------------------------------------

We install the official Supabase JavaScript client:
  npm install @supabase/supabase-js

We create one file — src/lib/supabase.ts — that initializes the client:
  import { createClient } from '@supabase/supabase-js'
  export const supabase = createClient(URL, ANON_KEY)

That supabase object is then imported anywhere in the app that needs data.

Examples of what calling Supabase looks like in code:

  // Read all approved messages
  const { data } = await supabase
    .from('community_messages')
    .select('*')
    .eq('status', 'approved')

  // Submit a new message
  await supabase
    .from('community_messages')
    .insert({ name: 'Bryan', message: 'Great place!' })

  // Admin approves a message
  await supabase
    .from('community_messages')
    .update({ status: 'approved' })
    .eq('id', messageId)

  // Admin logs in
  await supabase.auth.signInWithPassword({ email, password })

It reads almost like plain English. The client handles converting these into
proper database queries behind the scenes.


--------------------------------------------------------------------------------
  ENVIRONMENT VARIABLES — KEEPING SECRETS OUT OF THE CODE
--------------------------------------------------------------------------------

The Supabase URL and anon key need to be in the app, but we don't want to
hardcode them directly in source files (which get committed to git and pushed
to GitHub for anyone to see).

Instead, we use a .env file — a special file that holds variables for the
local development environment. It is never committed to git (.gitignore excludes it).

Our .env will look like:
  VITE_SUPABASE_URL=https://your-project.supabase.co
  VITE_SUPABASE_ANON_KEY=your-anon-key-here

The VITE_ prefix tells Vite (our build tool) to make these available inside
the React app via import.meta.env.VITE_SUPABASE_URL.

For production (the live website), these same variables get entered into the
hosting platform's dashboard (Netlify or Vercel) under "Environment Variables".
The build process picks them up from there automatically.

Remember: the anon key is safe to expose publicly because RLS is what actually
controls access. The key alone can't do anything the policies don't allow.


--------------------------------------------------------------------------------
  SUMMARY — WHAT CHANGES ONCE THIS IS ALL WIRED UP
--------------------------------------------------------------------------------

  BEFORE (localStorage)               AFTER (Supabase)
  ─────────────────────────────────   ──────────────────────────────────────
  Data stuck in one browser           Data in the cloud, any device, any browser
  Admin password in source code       Supabase Auth with hashed credentials
  Photos as base64 in localStorage    Photos as URLs in Supabase Storage
  No cross-device sync                Real-time sync across all devices
  sessionStorage flag as auth guard   Real JWT session from Supabase Auth
  ~5-10 MB storage cap                Effectively unlimited
  Anyone can bypass the auth guard    RLS enforces access at the database level


--------------------------------------------------------------------------------
  CLOUDFLARE TURNSTILE — SETUP STEPS (DO WHEN YOU HAVE CLIENT'S CLOUDFLARE ACCESS)
--------------------------------------------------------------------------------

Turnstile is Cloudflare's bot protection. It runs invisibly in the background
when the admin login page loads and verifies the visitor is a real human before
Supabase even checks the password. Bots can't generate a valid token so they
never get a chance to brute force the password.

NOTE: The client's domain (forgesalem.com) is on the CLIENT'S Cloudflare
account, not yours. You need access to their account to add the domain to the
Turnstile widget. Coordinate with the client before attempting this step.

  STEP 1 — Create the Turnstile widget (Cloudflare)
  ───────────────────────────────────────────────────
  1. Log into the CLIENT'S Cloudflare account at dash.cloudflare.com
  2. Click Turnstile in the left sidebar
  3. Click Add site
  4. Fill in:
       Widget name:  Forge Salem
       Hostname:     forgesalem.com  (add localhost as well for local dev)
       Widget type:  Managed
       Pre-clearance: No
  5. Click Create
  6. Copy both keys:
       Site Key   — goes in the frontend (.env file), safe to expose
       Secret Key — goes in Supabase, never put this in frontend code

  STEP 2 — Enable Turnstile in Supabase
  ───────────────────────────────────────
  1. Go to Supabase dashboard → Authentication → Settings
  2. Scroll to "Enable Captcha protection"
  3. Toggle it ON
  4. Select Cloudflare Turnstile from the dropdown
  5. Paste the Secret Key from Step 1
  6. Save

  STEP 3 — Add the Site Key to .env
  ───────────────────────────────────
  Add this line to the .env file (and to Netlify/Vercel environment variables
  when deploying):
    VITE_TURNSTILE_SITE_KEY=your-site-key-here

  STEP 4 — Install the Turnstile React package
  ──────────────────────────────────────────────
  Run in the project directory:
    npm install @marsidev/react-turnstile

  STEP 5 — Wire it into AdminLoginPage.tsx
  ─────────────────────────────────────────
  Tell Claude Code: "Wire up Cloudflare Turnstile into the admin login form
  using the VITE_TURNSTILE_SITE_KEY env var." It will know what to do from
  the SUPABASE_EXPLAINED.txt context.

  HOW IT WORKS ONCE SET UP
  ─────────────────────────
  - Turnstile loads invisibly when the login page opens
  - It generates a token proving the visitor is a real human
  - On form submit, that token is sent to Supabase alongside the password
  - Supabase verifies the token with Cloudflare before checking the password
  - A bot script has no way to generate a valid token, so it gets blocked
  - You as the real admin never see or interact with it — it's fully invisible

  IF SOMETHING BREAKS
  ────────────────────
  If Turnstile causes login issues after setup:
  1. Go to Supabase → Authentication → Settings
  2. Toggle "Enable Captcha protection" OFF temporarily
  3. This instantly disables Turnstile without touching any code
  4. Debug from there
